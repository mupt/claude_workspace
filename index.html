Field notes — Raspberry Pi 5

Running Claude Code
on bare metal.

Getting Claude Code to run reliably as a headless, always-on remote control service on a Raspberry Pi required solving five distinct problems. This is what it took.

01 The Problem

Claude won't start unattended.

claude remote-control shows interactive prompts on first run — workspace trust dialogs, remote control confirmation. A service can't answer those. The binary needs a TTY that isn't there.

~/.local/bin/claude-service-wrapper
Python · pexpect

A Python wrapper using pexpect that spawns claude remote-control with a fake TTY, watches for known prompts, and answers them automatically. Once past the prompts it steps back and lets Claude run, forwarding SIGTERM/SIGINT so systemd can stop it cleanly.

# spawns claude with a pty so it thinks it has a terminal child = pexpect.spawn( '/home/allmind/.local/bin/claude', args=['remote-control'], dimensions=(50, 220), timeout=None, ) # auto-answer interactive prompts child.expect(r'Enable Remote Control\? \(y/n\)') → sendline('y') child.expect(r'Yes.*trust.*folder') → sendline('') # Enter

A full test suite at test_claude_service_wrapper.py covers all prompt scenarios and signal forwarding using a fake claude binary — no real Claude needed.

02 The Problem

It needs to start on boot. Nobody will be logged in.

Claude runs as a user process, not root. Normal user services only start when the user logs in. The Pi boots headless into an empty shell.

~/.config/systemd/user/claude.service
systemd user

A user-level systemd service with Restart=always so Claude auto-restarts after crashes. Lingering is enabled so the user session (and its services) starts at boot without requiring a login.

# enable lingering — user services start without login loginctl enable-linger allmind # the service unit [Service] ExecStart=/home/allmind/.local/bin/claude-service-wrapper Restart=always RestartSec=5 EnvironmentFile=%h/.claude/secrets # ANTHROPIC_API_KEY lives here
useful ops
commands
systemctl --user status claude systemctl --user restart claude journalctl --user -u claude -f
03 The Problem

Sessions die silently. No one knows.

Claude can be alive as a process but completely disconnected — socket gone, session dead. Restart=always doesn't help if the process is still running. The Pi needs to notice and recover on its own.

/usr/local/bin/claude_watchdog.sh
systemd timer · root

Runs every 5 minutes as root. Checks for active TCP connections to 160.79.104.10:443 (Anthropic API) using ss. Two consecutive misses (~10 minutes) triggers a reboot.

# the whole detection logic ss -tn | grep -q "160.79.104.10:443" # if found → reset counter, exit 0 # if not found → increment /run/claude_watchdog_failures # if failures ≥ 2 → check cooldown, then reboot
reboot safety rails
rate limiting

A watchdog that reboots without limits is a watchdog that can brick itself. Two safeguards prevent that.

30-minute cooldown
Last reboot timestamp written to /var/lib/claude-watchdog/last-reboot (persists across reboots). If less than 30 minutes have elapsed, skip reboot and log. Prevents infinite reboot loops during Anthropic outages.
Max 2 reboots per hour
All reboot timestamps appended to /var/lib/claude-watchdog/reboot-log. If 2 or more entries exist within the last 60 minutes, hard-stop — no reboot.
10-minute boot grace period
Checks /proc/uptime and exits immediately if system uptime < 600s. Gives Claude time to connect before the watchdog starts judging.
persistent journal logging
diagnostics

By default, systemd journal is ephemeral — gone on reboot. After a watchdog-triggered reboot, the logs that explain why it rebooted are lost.

# /etc/systemd/journald.conf Storage=persistent # survives reboots # diagnose the previous boot journalctl -b -1 | tail -50 journalctl -t claude-watchdog -f
04 The Problem

The kernel can freeze. Software can't save you.

If the kernel panics or systemd itself hangs, no amount of shell scripts will help. The Pi has a hardware watchdog baked in. It just needs to be armed.

BCM2835 hardware watchdog
hardware

systemd can pet the hardware watchdog device at /dev/watchdog0. One config line enables it. If systemd stops petting — kernel freeze, OOM, deadlock — the hardware forces a reboot after its timeout expires.

# /etc/systemd/system.conf RuntimeWatchdogSec=15 # systemd pets it every 15s # hardware timeout is 60s # if 4 consecutive pets missed → hard reboot # verify it's armed sudo wdctl # shows device, timeout, timeleft journalctl -b -k | grep watchdog

05 The Problem

Every reboot wipes Claude's memory.

The watchdog keeps the Pi running. The service keeps Claude running. But every time the session restarts, all context — ongoing work, decisions, preferences — is gone.

file-based memory system
persistence

A structured memory directory holds context that persists across sessions. An index file (MEMORY.md) points to typed memory files. CLAUDE.md instructs Claude to read all of them at the start of every session.

# ~/.claude/projects/-home-allmind/memory/ MEMORY.md # index — loaded automatically project_claude_watchdog.md # watchdog design, files, behaviour project_session_continuity.md # how the memory system itself works # ~/CLAUDE.md — runs at session start "At the start of every new session, read ALL files in /home/allmind/.claude/projects/-home-allmind/memory/"
~/.claude/commands/save.md
/save command

A custom slash command /save triggers a full context save before ending a session. Reviews the conversation and writes structured memory files — user profile, ongoing work, decisions, open questions — so the next session picks up exactly where this one left off.
